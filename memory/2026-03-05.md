### FiberQuest — Console Hub Research
Phill proposed a new angle: ESP32-S3/P4 as a **central console hub** that emulates native console multiplayer link protocols so games play together "as intended" — no modifications, invisible payment layer underneath.

#### Key findings from 5 new research tasks:

**ESP32-P4 — confirmed ideal chip:**
- Dual-core RISC-V 400MHz (vs S3's 240MHz), 50+ GPIOs, 768KB SRAM + 32MB PSRAM support
- 8KB zero-wait TCM RAM + ETM (Event-Task Manager) — hardware-level microsecond timing without CPU
- USB OTG HS 480Mbps — connect modern USB controllers directly
- SPI x3, UART x3, RMT — maps well to console protocols
- P4 is significantly better than S3 for real-time protocol emulation

**Console link protocols:**
- Game Boy Link Cable: SPI-like synchronous serial, master/slave via clock, 8-bit bytes → ESP32 SPI peripheral maps well; **5V logic → needs TXS0108E level shifter**
- SNES controller: Shift register polling via LATCH/CLOCK/DATA → RMT peripheral ideal, ~120Hz
- NES Four Score: Shift register + strobe → RMT suitable
- Voltage: All these consoles are 5V; ESP32 is 3.3V — level shifting required on all lines
- N64 Joybus, GBA link, Genesis: not found in seeds — need manual research

**No prior art found:** Zero existing ESP32 projects doing SNES/Game Boy link emulation on GitHub searches. Genuinely unexplored territory.

**Recommended MVP demo:** One SNES with two controllers → ESP32-P4 reads both → button press triggers Fiber micropayment → display shows live balances. Games don't know anything changed.

**Recommended hackathon approach: Hybrid**
- RetroArch handles emulation (saves huge dev time)
- Small ESP32-P4 board reads real console controllers + integrates Fiber payments
- Outputs to RetroArch via USB HID
- Best judge impact per hour of development

**Post-hackathon commercial vision:** Universal retro controller adapter + invisible Web3 payments. Arcade operators, retro enthusiasts. Open hardware + protocol standard.

### Fiber vs CKBFS — Important Clarification
- Research crawler (Gemini) hallucinated "Fiber Archive Agent" concept — confused two things:
  1. `nervosnetwork/fiber-archive` = old abandoned GitHub repo (2021), "archived" = GitHub flag
  2. CKBFS = actual CKB cell-based file storage (what we use)
- **Fiber CANNOT store data** — it's a payment channel network (like Lightning)
  - Only channel open/close txs touch L1; everything between is off-chain message passing
  - No user data stored, no file storage capability
- **CKBFS stores data** — files chunked across CKB cells, fully on L1
- Correct mental model: Fiber = money pipe, CKBFS = storage layer, CKB L1 = anchoring
- FiberQuest architecture is correct: CKBFS stores game content, Fiber routes payments

- NES emulator needs ~100–200 KB → 500+ KB headroom remaining
- **Memory concern is off the table for FiberQuest P4 coexistence**

### ESP32-P4 WiFi — Onboard vs SPI Coprocessor
- Phill asked about using ESP32 coprocessor as a test proxy for onboard WiFi timing
- Key distinction:
  - **Onboard WiFi**: interrupts fire directly on RISC-V cores (~1–5μs ISR), real production scenario
  - **SPI coprocessor**: P4 only sees SPI interrupt when data ready — 10–100× lower interrupt load, faster path
- Coprocessor test = optimistic/best-case — if it causes frame drops, onboard will be worse
- **Recommendation: test on real P4 hardware directly**
- ESP32-P4-Function-EV-Board ironically uses ESP32-C6 coprocessor over SPI for WiFi
- For native onboard WiFi need: WT9932P4-TINY or similar module with combo chip
- Phill considering ordering a WiFi-enabled P4 board
