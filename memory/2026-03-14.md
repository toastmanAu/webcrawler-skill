# FiberQuest Architecture Decision — Agent Handler Model

**Date:** 2026-03-14
**Decision:** Escrow wallet controlled by dedicated FiberQuest Agent, not website backend

## Key Points

✅ **Escrow in Agent (not Website)**
- Website: Read-only, no private keys
- Agent: Holds CKB_ESCROW_PRIVATE_KEY, controls all funds
- Benefits: Deterministic, secure, 24/7 monitoring

✅ **Continuous Monitoring**
- Agent polls escrow address every 6 seconds (one block)
- Detects payment arrivals
- Updates shared tournament database

✅ **Auto-Publishing at Block Cutoff**
- Agent checks block height
- If min entrants met: publishes to CKB + opens Fiber channel
- If min not met: refunds all players
- No manual intervention needed

✅ **Prize Settlement**
- Agent monitors for validator proofs
- Verifies signature + winner
- Settles Fiber channel automatically
- Winner receives CKB instantly

## Architecture

```
Website                          Agent                    CKB/Fiber
├─ Landing page                 ├─ Escrow monitor        ├─ Node
├─ Tournament browser           ├─ Auto-publisher        ├─ Light client
├─ Join form                    ├─ Fiber manager         └─ Network
└─ Account dashboard            └─ Settlement logic
    ↓                                ↓
    └─ Shared Database (tournaments, entrants, validations) ─┘
```

**Separation of Concerns:**
- Website: User-facing UI, authentication, browsing
- Agent: All blockchain operations, fund handling, settlement
- Database: Shared truth for tournament state

## Why This Approach?

1. **Security** — Private key never exposed to web tier
2. **Reliability** — Agent runs 24/7, not just when website gets requests
3. **Simplicity** — No complex async polling in website
4. **Cost** — Free local inference instead of API calls
5. **Auditability** — All fund moves logged + deterministic

## Agent Hosting Decision (15:53 GMT+10:30)

**Chosen:** Pi 5 (new dedicated NVMe machine) as sole host for website + agent

**Rationale:**
- Standalone, dedicated, no shared resource contention
- NVMe SSD = faster, more reliable than SD card
- Integrated display (unused but available)
- More powerful than OPi3B, cleaner than shared NucBox setup

**Inference Sources:**
- Primary: NucBox Ollama (192.168.68.79:11434) via HTTP
- Fallback: HuggingFace free tier (qwen2.5, llama, deepseek)
- Safety: Agent never sends private keys to external service; inference only for optional monitoring/logging

## OS Choice for Pi 5 + NVMe (15:43-16:00 GMT+10:30)

**Initial decision:** Ubuntu Server arm64 (server-optimized)

**Revised decision (16:00):** Ubuntu Desktop arm64

**Why Desktop:**
- RetroArch emulation on same machine (needs GUI)
- Demo everything locally on one screen
- Better user experience for testing + presentation
- Still performant on NVMe + Pi 5 hardware
- OpenClaw fully supported on Desktop

**Performance implications:**
- Boot time: ~25-30s (minimal desktop overhead on NVMe)
- Idle RAM: ~350-400MB (lightweight desktop)
- No performance impact on background FiberQuest Agent service
- FiberQuest Agent runs as systemd service (silent, 24/7)

**Complete Pi 5 System:**
- FiberQuest website (port 3000) — Next.js backend API
- FiberQuest Agent (background) — escrow monitoring, auto-publish, settlement
- RetroArch — game emulation + testing
- Postgres database — shared between website + agent
- GUI desktop — local demo + test sessions

**Setup:**
- Flash Ubuntu Desktop arm64 to USB
- Boot Pi, install to NVMe
- apt install nodejs postgresql retroarch
- Clone FiberQuest repos
- Systemd service for agent (runs in background)
- GUI for interactive demo

## Radxa X4 Hardware Update (16:42 GMT+10:30)

**Found:** 2230 1TB NVMe on Radxa X4 (was hot)
**Solution:** MOSFET PWM on 50mm case fan for thermal control
**Benefit:** Cooler operation = more stable, longer SSD lifespan

**Setup:**
- GPIO PWM to MOSFET gate
- Fan speed scales with NVMe temperature
- Monitor via `hwmon` sysfs
- Systemd service to manage fan daemon

**Impact on FiberQuest:**
- If using Radxa X4 for agent instead of Pi 5: thermal mgmt solved
- NVMe now actively cooled (better reliability for 24/7 operation)
- Fan PWM can be tied to agent monitoring (optional)
